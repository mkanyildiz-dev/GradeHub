Systems Integration Functional Specification
Integration project group 4
1	Summary
This project implements an automated Student Grade Sync & Notification System. When a professor submits a grade through a Moodle-style web form, the grade is automatically forwarded to the Campus Information System (CIS) via a SOAP web service, and the affected student receives an email confirmation. The integration bridges two independent systems using two different technologies; a RESTful API (Moodle) and a SOAP/WSDL-based service (CIS), connected through a C# .NET 8 integration middleware. The project simulates a realistic university workflow that eliminates manual data transfer between the learning management system and the student records system.
2	Stakeholders
The project is developed by a team of 4 students from FH Technikum Wien. Each member is responsible for one of the core components and shares responsibility for documentation, testing, and the final live demonstration.
Development Team: ASP.NET Core REST API (Moodle simulation) and integration service
Development Team: SoapCore SOAP service (CIS simulation) and WSDL definition
Development Team: Email notification module, end-to-end testing, and demo orchestration
End user (simulated): Professor submits grades via the Moodle form
End user (simulated): Student receives an automated email confirmation
3	Functional overview
The system consists of two independent systems connected by an integration middleware. Moodle acts as the source system where grades are submitted via a RESTful HTTP interface. The integration middleware receives this data, transforms it into a SOAP/XML message, and forwards it to the Campus Information System (CIS) for permanent storage. After successful storage, the middleware triggers an email notification to the affected student. The end-to-end flow is illustrated below:
Professor → [Moodle REST API] → [Integration Middleware] → [CIS SOAP Service] → Email → Student
Data is transmitted as JSON over HTTP between Moodle and the middleware, and as XML over SOAP between the middleware and CIS. The email notification is sent via SMTP.


 
3.1	Involved systems
3.1.1	System 1 Moodle (REST)
Moodle represents the Learning Management System where the professor submits grades. In this project, Moodle is simulated by a lightweight ASP.NET Core Minimal API web application that exposes a REST endpoint at POST /grade. The professor accesses a simple HTML form, fills in the student ID, course code, and grade, and submits it. The ASP.NET Core endpoint receives the request as JSON and forwards the data to the integration middleware. Technology: C# / ASP.NET Core (Minimal API, .NET 8). Interface: RESTful HTTP API. Data format: JSON. Port: 5000.
3.1.2	System 2 CIS (SOAP)
The Campus Information System (CIS) is the official student records system of the university. In real life this would be CAMPUSonline or a comparable ERP platform. In this project, CIS is simulated by a C# SOAP service built with the SoapCore library on ASP.NET Core. It exposes a WSDL-defined operation storeGrade(studentId, courseId, grade) that receives the grade data as an XML message, validates it, and appends the record as a new line to a local CSV file (grades.csv) which acts as the simulated records store. The WSDL document is automatically generated by SoapCore and can be inspected via SoapUI for the live demonstration. Technology: C# / SoapCore on ASP.NET Core (.NET 8). Interface: SOAP/WSDL. Data format: XML. Port: 8000.
3.1.3	System 3 Integration Middleware
The integration middleware is the central orchestrator that connects the two independent systems. Implemented as a C# .NET 8 console application, it receives the JSON grade data from the ASP.NET Core REST API, transforms it into a SOAP request, calls the CIS SOAP service, and on success triggers an email notification to the student via SMTP using MailKit. The middleware also handles error cases such as SOAP faults or SMTP failures with retry logic. Technology: C# / .NET 8 console application (HttpClient, generated SOAP service reference, MailKit for SMTP). Role: data transformation and routing.

3.2	Use Cases
The integration is described through four use cases that cover the end-to-end grade submission flow, including error handling. Each use case lists its purpose, the involved systems, and the structure of the exchanged data.
•	UC1 Submit Grade via Moodle (REST)
Purpose: The professor submits a student grade through the Moodle web form, which is received by the ASP.NET Core REST API.
Short description: The professor submits studentId, courseId, and grade via an HTTP POST to /grade. The ASP.NET Core app validates the payload and forwards it to the integration middleware.
Involved systems: Moodle (ASP.NET Core REST API), Integration Middleware
Structure of exchanged data: JSON payload { "studentId": "st1234", "courseId": "SYIN", "grade": "1" }

•	UC2 Sync Grade to CIS (SOAP)
Purpose: The integration middleware forwards the validated grade to the CIS SOAP service for persistent storage in the simulated student records system (CSV file).
Short description: The middleware constructs a SOAP envelope and calls storeGrade(studentId, courseId, grade) on the CIS service. CIS validates the input, appends the record as a new row to its local CSV file (grades.csv), and returns a success confirmation.
Involved systems: Integration Middleware, CIS (SoapCore SOAP service)
Structure of exchanged data: SOAP/XML 
<storeGrade><studentId>st1234</studentId><courseId>SYIN</courseId><grade>1</grade></storeGrade>

•	UC3 Send Email Notification to Student
Purpose: After the grade has been successfully stored in CIS, the student receives an automated email notification confirming the grade entry.
Short description: On a successful SOAP response from CIS, the middleware sends an email to the student via SMTP. The email contains the student ID, course name, and the recorded grade.
Involved systems: Integration Middleware, Email Service (Gmail SMTP)
Structure of exchanged data: Plain-text email; Subject: "Grade recorded for SYIN"; Body: "Your grade for Systems Integration has been officially recorded: 1"

•	UC4 Error Handling & Retry
Purpose: Ensure reliability when the CIS SOAP service or the SMTP server is temporarily unavailable, so that no grade submission is silently lost.
Short description: On a SOAP fault or SMTP connection error, the middleware logs the failure, waits five seconds, and retries up to three times. After three failed attempts, the error is written to a persistent log for administrator review.
Involved systems: Integration Middleware (logging only — no external systems)
Structure of exchanged data: Local log entries (timestamp, error type, payload, retry count)
